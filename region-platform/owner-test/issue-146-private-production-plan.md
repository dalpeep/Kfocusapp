# Issue #146 독립 온라인업소록 비공개 운영 전환

## 배포 전 상태

Colorado QA는 별도 Netlify 사이트와 owner-test 데이터베이스를 사용한다. 지역 생성과 브랜딩, 관리자 및 업주 업소 등록·수정, 승인, 소유권 신청, 이미지, 기능별 설정, 검색, 지도, 커뮤니티 분류와 지역 권한 검사가 있다. 화면은 모바일 우선 앱 셸과 홈/업소/쿠폰/지도/가이드 하단 메뉴를 유지한다. Issue #146은 공개 승인 업소 상세와 직접 요청 검사를 추가했다.

커뮤니티는 목록과 분류를 제공한다. 글쓰기·댓글, 추천/신규/인기 정렬, 예약, 승인 알림, 지역 관리자 배정·해제는 미연결이다. 쿠폰·할인·프로모션·이벤트는 목록만 제공하며 등록·승인 워크플로는 미연결이다. 실제 운영 공개를 승인할 때 필수 범위를 확정해야 한다.

## 승인 요청 범위

1. Dallas 운영과 별도인 Netlify 팀 또는 프로젝트를 만든다. 기존 팀의 공용 환경 변수 목록을 점검하고 운영 Dallas나 QA 자격 증명이 상속되지 않는 프로젝트에만 연결한다. 승인 전 도메인을 구매하지 않는다. 최초 주소는 네이티브 Netlify 하위 도메인으로 시작하며, `online-business-directory`는 가용성을 확인해야 할 후보 이름이다. 사이트의 팀 보호를 켜고 권한을 부여한 운영 관리자만 최초 접속하도록 한다.
2. 별도 Supabase 조직에 운영 프로젝트 1개를 만든다. 초기 미국 리전 후보는 기술·계정 가용성을 확인한 뒤 확정한다. 요금 변경 전 대시보드에서 실제 총액과 초과 한도를 확인한다. Dallas와 owner-test 데이터 및 사용자, Storage 객체를 가져오지 않는다.
3. 신규 운영 프로젝트에만 운영용 스키마, 지역·업주·관리자 멤버십, RLS, 감사 로그 및 이미지 정책을 적용한다. QA Basic 인증과 리전 JSON RPC를 그대로 운영에 복제하지 않는다. 초대 기반 Supabase Auth와 서버 세션으로 전환하고, 관리자의 지역 권한을 서버와 DB에서 재검증한다. OAuth 선택 시 운영 URL만 콜백으로 등록하며 사용할 공급자와 초대 계정은 승인 후 확정한다.
4. 운영 환경 변수를 전용으로 만들고 서버 설정에서 운영 프로젝트 ref와 호스트를 검증한다. 일치하지 않으면 시작하지 않도록 한다. 비밀은 운영 서버 전용으로 보관한다. 사진 저장 및 메일 공급자 설정은 별도 확인한다. 비공개 운영 앱에 Colorado 주 전체 구성을 빈 데이터로 시작하고, Denver/Aurora는 선택 가능한 프리셋으로 유지한다.
5. 운영 사이트를 공개하기 전에 관리자가 접속 가능한 비공개 빌드에서 390px·1440px, 계정별 권한, 교차 지역 요청, 토글·복원, 등록→승인→상세, 이미지, 배포 롤백을 확인한다. 이후 공개 전환은 별도 검수로 진행한다.

## 롤백

새 운영 Netlify 게시를 중단하거나 검증된 이전 배포로 되돌린다. 운영 DB에 문제가 있으면 신규 쓰기를 먼저 정지하고 DB를 별도로 보존한 뒤, 복구를 검토한다. 초기 배포는 QA와 독립하므로 기존 Colorado QA와 Dallas는 계속 기존 주소와 자격 증명을 사용한다. 프로젝트 해지·데이터 삭제·도메인 이전은 별도 승인 대상이다.
