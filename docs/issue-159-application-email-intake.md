# 신청 이메일 인증 변경 검토

공개 업소 등록과 광고 문의는 브라우저가 `business_requests`와 `advertising_requests`에 직접 저장합니다. 업주 포털의 신규 신청은 별도 경로를 사용합니다. 공개 신청 테이블에는 일반 사용자의 직접 쓰기를 허용하는 정책이 있어 화면에서만 인증을 요구하면 기존 API를 통해 우회할 수 있습니다.

## 배포 승인 범위

1. 기존 `business_mail` 비공개 스키마에 신청 증빙 테이블을 추가합니다. 이메일 주소, 신청 경로, 토큰 해시, 유효 기간, 인증·동의 시각과 동의 문구 버전, 접수 식별자를 저장합니다. 기존 업소의 인증·동의값은 일괄 입력하지 않습니다.
2. 인증된 증빙을 요구하는 서버 접수 트랜잭션을 적용하고 공개 테이블에 대한 직접 접수 우회를 차단합니다. 업주 포털의 `new` 경로에도 적용합니다. 초안 SQL은 증빙 처리만 포함하며 접수 강제 정책은 적용하지 않습니다.
3. 공개 발급에는 수신 주소별 재발송 간격, 전체 한도, 기존 봇 검증을 적용합니다. 이메일에서는 링크를 열고 확인 버튼을 눌러야 인증됩니다. 홍보 동의는 기본 해제 상태입니다. 신청 접수 때 인증된 주소가 현재 주소와 다르면 새 인증을 요구합니다.
4. 신청 관리에는 접수 시점의 증빙을 표시합니다. 실제 업소가 연결될 때만 해당 업소 UUID와 현재 등록 이메일이 일치하는 증빙을 발송 관리 상태에 반영합니다. 업소와 연결되지 않은 광고 문의는 신청 관리에만 표시합니다. 동일 이메일을 쓰는 다른 업소에 동의를 전이하지 않습니다.
5. 기존 접수 행은 인증 도입 전 상태로 표시하고 기존 수동 확인 절차를 유지합니다. 기존 접수 알림의 `AFTER INSERT` 트리거는 인증이 끝나 최종 접수된 행에서 기존 방식으로 한 번 실행됩니다. 예약 알림과 작업 #24는 변경하지 않습니다.

롤백 순서는 신청 화면과 업주 포털의 이전 버전을 복원하고, 새 접수 강제 정책을 해제한 뒤 기존 접수 권한을 복원하는 방식입니다. 인증 토큰 발급을 중단하고 증빙과 동의 이력은 보존합니다.

## 기존 직접 신청 건 처리

운영 읽기 전용 대조에서 공개 업소 등록 신청 기록 21건 중 14건이 Dallas 업소의 이름 및 현재 이메일과 일치했습니다. 중복 신청을 업소 UUID와 이메일로 묶으면 8곳입니다. 인증과 홍보 수신 동의 증빙은 각각 0건이었습니다.

기존 신청에 업소 UUID가 없으면 이름과 현재 이메일이 모두 일치하고 결과가 유일한 경우만 연결 후보로 표시합니다. 관리자가 확인한 연결을 저장하며, 이름이나 주소가 바뀌었거나 둘 이상 일치하면 수동 검토 대상으로 남깁니다. 구글맵 수집 여부는 장소 ID 유무로 판정하지 않고 신청 원본과 확인된 연결의 존재로 구분합니다.

인증 요청 대상은 승인 상태와 별개로 관리합니다. 요청 전 발송할 업소명과 주소, 중복 및 제외 사유, 제목과 본문을 표시하고 관리자가 확인하도록 합니다. 기존 인증값은 해당 업소 UUID와 현재 이메일에 해당하는 검증 증빙이 있을 때만 가져옵니다. 발송 클릭, 관리자 수동 확인, 기존 업소 승인 자체는 수신 동의 증빙으로 기록하지 않습니다.
