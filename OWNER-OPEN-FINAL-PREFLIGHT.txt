4. Worker 구성
owner-notification-worker는 Native default export, config.schedule=*/5 * * * *.
기존 4개 스케줄 변경 없음. 공유 Supabase SDK 포함 설정을 사용한다.
명시적 활성화 이전에는 SDK/DB/Provider 호출 전 disabled로 반환한다.
활성화 시 OWNER_UUID 환경 검증과 actor/business/recipient allowlist가 필수.
OWNER_NOTIFICATION_MODE=mock으로 시작. 실제 발송은 resend_test만 허용.
최대 3건/실행, 처리 루프 18초 한도(개별 호출 시간 별도), Provider 5초,
RPC 3초 타임아웃. DB lease 2분, 최대 5회, 재시도 지수 backoff.
23시간 이후 자동 재발송 중단/review. Resend idempotency 24시간과 구분.
응답은 본문 없는 204/503; 로그는 집계 상태만, 수신자·본문·키 미출력.
Scheduled 실행은 Published에서만 가능하므로 미게시 빌드로 cron 실행
성공을 증명할 수 없다. 공식 빌드의 패키지/스케줄 검사와 구분한다.
기본 OFF여도 Published에서는 5분마다 호출되어 일 최대 288회 사용량 발생.

5. 제한 Canary 순서와 합격 기준
A. 최신 후보 Commit·Linux CI·아티팩트 고정(기존 44/4 + 신규 5/1).
B. 별도 승인된 미게시 공식 빌드: SDK 로딩, 스케줄, OFF, 비밀정보 검사.
C. 별도 SQL 승인과 백업 완료 후 마이그레이션. Owner/Worker OFF 유지.
D. 게시 승인 후 가상 업소 1개·명시적 테스트 계정·수신자만 허용.
   관리자도 actor allowlist에 포함. 새 업소 ID는 승인 후 명시적으로 추가.
E. mock으로 신청→승인/거절→쿠폰/이벤트 저장→큐→Worker ack 확인.
   403 타 업소/계정 차단, 같은 요청/lease 동시 처리 1회, retry/ack 복구 확인.
F. 별도 실제 발송 승인 후 지정 수신자 1명으로 제한. 기존 비밀 키 유지.
   호스팅된 Worker는 등록된 키를 직접 사용할 수 있으므로 키 원문 회수가
   반드시 필요한 것은 아니다. 다만 키 유효성/발신자 권한/도메인은 미검증.
   accepted는 수신 완료가 아니다. 수신함 확인 후에만 수신 PASS로 기록.
G. 테스트 데이터는 기존 기록과 구분, 감사 이력 보존. 끝나면 Owner/Worker OFF.
